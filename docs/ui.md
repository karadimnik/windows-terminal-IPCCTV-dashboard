# The control UI

Its four screens - Dashboard, Settings, Footage and Live - are described in the [README](../README.md#day-to-day); Live has its own section below.

## How it works

`camui.exe` is one Go binary with the whole UI embedded in it. **It owns no state.** Every number comes from `_state\status.json`, the same file the health strip reads, and every change goes through `cam.ps1` and `cam.recorder.ps1`. That is why the command line keeps working unchanged and why the two can never disagree about anything. Its Footage index is parsed from the filenames the recorder already writes, so there is no database and nothing opens a segment to list it; a clip is remuxed to fragmented MP4 on demand, video copied and only the 8 kHz audio transcoded, so playback keeps its sound.

**No camera credential ever reaches the browser.** Cameras are addressed by name, and no endpoint returns a relay or RTSP URL of any shape. The harness proves it rather than trusting it: the `uileak` check fetches every endpoint, a real clip included, and scans every byte for the password, for its URL-escaped form and for anything shaped like a credential in a URL, with a positive control proving the scanner can see one.

**Loopback only, deliberately.** `127.0.0.1` needs no `urlacl` and no elevation, and the binary **refuses to start** on any address that is not exclusively loopback unless an auth token of at least 16 characters is configured. Exposing it beyond this machine is therefore a deliberate act rather than something that can happen by accident. To do it, save this as `camui.config.json` next to `camui.exe` and restart the UI:

```json
{
  "listen": "0.0.0.0:8787",
  "token": "a-long-random-string-of-at-least-16-characters"
}
```

Nothing else has to change: the launcher passes that file if it exists, and `-Status` reports the address it found and where it read it from. Every request then needs the token, which can arrive once as `?token=...` and is moved into an HttpOnly cookie so it stops appearing in the address bar, in history and in any `Referer`. The scripts **do** read the token - `Get-CamUiRuntimeState` opens `camui.config.json` and looks at `CAMUI_TOKEN` to answer the one question `-Status` asks of it - but they never print it, log it or pass it on: `-Status` reports only whether one is configured. The token is never taken from a flag, because a command line is readable by every process on the machine.

**A web page you visit cannot drive it.** The UI sits on a fixed local address that a page in your own browser can reach, so every request passes a guard before anything else. The `Host` header must name `localhost`, `127.0.0.1` or `::1`; that is what stops DNS rebinding, where an attacker's name is pointed at `127.0.0.1` so that the browser treats camui as that page's own site. On `/api/` a request carrying `Sec-Fetch-Site` other than `same-origin` or `none`, or an `Origin` that is not the address it was sent to (`null` included), is refused with 403. A state-changing request (POST, PUT, PATCH, DELETE) that carries a body must be `application/json`, otherwise 415 - a browser cannot send that type to another site without a preflight, which camui never answers. A request with neither header, such as a script, `curl` or the test harness, passes these checks and is still subject to the token if one is set. Responses under `/api/` carry `Cross-Origin-Resource-Policy: same-origin`, `X-Content-Type-Options: nosniff` and, unless the handler sets its own, `Cache-Control: no-store`. The page and its assets are subject only to the `Host` check. A refusal is logged once, with the method, path and reason, and never a header value or a body. The `uiguard` check proves all of it against the real binary.

In the exposed setup above (non-loopback `listen` and a token) the `listen` host is allowed as a `Host` too. A wildcard bind (`0.0.0.0` or an empty host) has no single address to name, so any IP-literal `Host` is allowed instead - an IP literal cannot be rebound. To reach it by a **name** (`nvr.lan`), list the name, port ignored, in `allowedHosts`:

```json
{
  "listen": "0.0.0.0:8787",
  "token": "a-long-random-string-of-at-least-16-characters",
  "allowedHosts": ["nvr.lan"]
}
```

`allowedHosts` is optional, empty by default and read from the config file only. Browsers on other machines reach camui by a name or an address you chose, so a name that is missing from the list gets a 403 from the guard rather than a login prompt.

**How it runs.** The `IPCCTV-Ui` logon task runs a generated launcher at `%LOCALAPPDATA%\IPCCTV\start-ui.ps1`. The launcher waits for `camui.exe` to be reachable, exactly as the recorder's launcher waits for the scripts, then starts it in a console of its **own** with no window. That last part is not cosmetic: a console created with a window is handed to Windows Terminal as a tab in the window that already exists, and closing that window would take the UI with it. It starts nothing at all if the address is already being served, so a second start cannot fight the first one for the port, and it exits non-zero if nothing is serving afterwards, which hands the retry to the task's restart policy.

camui logs to stdout only, so a thin `powershell.exe` holds the pipe and appends it to `%LOCALAPPDATA%\IPCCTV\camui.log`. **The roll happens in the launcher, not in a running UI:** at every start it checks that file, and if it is past 10 MB it renames it to `camui.log.prev` - replacing any previous `.prev` - and starts a fresh one. A UI that stays up for weeks therefore keeps appending to one file past 10 MB, with a line per request and nothing to bound it; stopping and starting it is what rolls the log. The launcher's own log is `autostart-ui.log` beside it, and that one has no rotation at all - it gets a handful of lines per start, so it grows slowly, but it grows forever. Delete either by hand when it is in the way; nothing reads them back.

The binary is never copied anywhere, so a rebuild takes effect the next time the UI starts, with no reinstall. Stop it before rebuilding and start it again afterwards: a running process keeps the code it started with, and with the repository on the WSL share the write is not refused the way Windows refuses to overwrite a running binary on a local drive. `cam.ps1 -Stop` does not stop the UI, which is the point - the thing you start everything from should still be there after you have stopped everything. When you do want it gone, `-Status` prints the pid that owns the port.

## The web app inside `holocron`

The Go system (`holocron.exe`, built by `build-holocron.sh`) runs this same web app as its **web role**; nothing about the page, the Host/Origin guard, the token, the LAN login, the read-only default or the WHEP exception differs. `holocron up` starts it as a managed child of the host once the supervisor is started (`holocron up --only host` starts none), and `holocron down` stops it with the rest and counts it. `holocron web` runs it alone (diagnostics) and takes every `camui.exe` flag below and the same config file. Its defaults come from `holocron.config.json`: `web.enabled` (default true), `web.listen` (default `127.0.0.1:8787`), `web.tlsListen`, `web.tlsDir`, `web.authDir` (keys in `internal/config/KEYS.md`); the camui flags and `-config` file override them. A web crash never touches the recorder: the host restarts only the web child, after 5 s, then 10, 20, 40, 60 s (reset by 5 minutes of health), with a WARN each time and alert 104 when it crashes 5 times in 30 minutes; a supervisor restart never restarts it. `holocron status` shows the web role (pid, listen address, whether the HTTPS listener is on, whether a login exists).

**How its buttons act.** The page changes things only through a *controller*, chosen per request (and kept for 5 s): when `<root>\_state\ctl.addr` exists and answers within 1 s, the **API controller** (the supervisor's control API: Stop is `POST /v1/stop`, the record toggle `POST /v1/cameras/{name}/record`); otherwise the **PowerShell controller**, exactly as before (`cam.ps1`, `cam.recorder.ps1`, `schtasks`). A stopped Go system cannot be started from the page: Start answers 409 "start it with holocron up (or your service manager)", except in the `holocron web` role, where it runs `holocron up --detach` with the web role's own `--root`/`--config`. In the Go system the page's settings writes (`PUT /api/cameras`, `PUT /api/config`) are refused with 501 and the message to use `holocron cam` and `holocron config set`; they are still the PowerShell writer for the old system. Every request that changes something is a logged action (`web.control`, `web.record`, `web.cameras.put`, `web.config.put`, `web.acknowledge`, `web.login`, `web.logout`, `web.setup`, `web.live.create`, `web.live.delete`) with the actor `web:<user>`, `web:loopback` or `web:anonymous`, and goes to `audit.log`; request lines are DEBUG records of component `web`.

## Live view

The **Live** tab (beside Dashboard, Settings and Footage) shows the cameras as a tile grid that fills the window. It needs live view switched on and running; with `LiveViewEnabled` false (the default) the tab says so and nothing else changes - no process is started, no camera session is used, and every other screen behaves as before.

**What it shows.** Each tile plays the camera's second stream (`LiveSubStream`, small and cheap) with the camera name, a state chip (**Connecting**, **Live**, **Offline** - no picture from that camera, or the connection was lost - or **Error**) and an **Unmute** button, all drawn over the picture so they take no tile height. Sound is **muted** until you press that tile's Unmute. A failed connection retries with a growing delay (1 to 15 seconds).

**The grid fills the window.** On the Live tab the page has no side margins to speak of (6 px) and the tiles are 4 px apart. The column count is chosen to make the 16:9 pictures as large as the window allows (`bestGrid` in `live.js`: for every column count the tile width is the smaller of the width share and the height share, the largest wins, a tie goes to fewer columns) and is recomputed on every resize, rotation and fullscreen change. At 1920x1080 that is 3x2 tiles of 633x356 with no scrolling; at 2560x1440, 846x476; at 800x1000, 2 columns; on a phone (a best fit narrower than 300 px) 1 column, full width, and the page scrolls. In **Fit** (the default) pictures are never cropped (`object-fit: contain`). Six 16:9 pictures cannot cover a 1920x1040 area completely: the tiles use the full width and about 69 % of the height; the rest is the shape of 16:9, not unused layout - **Fill** (next paragraph) uses it. **Fullscreen** (top right of the Live tab; hidden where the browser has no Fullscreen API) puts the grid alone on the screen so the header and tabs disappear; Esc or the button in the corner leaves it.

**Fit or Fill.** Two buttons beside Fullscreen choose how the grid uses the window; the choice is stored in this browser's `localStorage` (`camui.live.fit`, `fit` or `fill`), survives a reload, and each browser (and each profile) keeps its own. The default is **Fit**, the layout above. **Fill** is for a wall that should use the whole screen: `bestGridFill` in `live.js` divides the entire grid area (the window below the toolbar down to the 6 px page padding, or the whole screen in fullscreen) into cells, tile = cell (not 16:9), and the picture is scaled to cover its cell (`object-fit: cover`), so its edges are cropped. For every column count whose cell is at least 300 px wide and 180 px tall it computes the share of the picture that would be cut off (`1 - min(a, 16/9) / max(a, 16/9)` for the cell's aspect `a`); the smallest crop wins and a tie goes to fewer columns. Name, state chip and Unmute stay drawn over the picture inside the cell. Measured with six 640x360 pictures in Chrome 155 and Edge 155: at 1920x1080 **3x2 cells of 633x495** (Fit: 633x356) covering 99.4 % of the window width and of the grid height with no scrolling, each picture cropped by **28 %** (the sides; the full height shows); at 800x1000 2x3 cells of 392x302, 27 % cropped; computed for 2560x1440 3x2 of 846x663, 28 %. The crop depends only on the cell shape, so it is the same for every camera: 6 cameras in a 16:9 window crop 26 to 28 %, 4 cameras (2x2) about 10 %, 1 camera about 10 %, 2 cameras 45 %. When the count does not divide evenly (5 cameras in 3x2) the last cell is empty. **Phone rule:** a portrait phone keeps one column; Fill divides the height among the tiles only if each stays at least 180 px tall (computed: up to 3 cameras on a 390x844 phone, whose grid area is about 684 px tall), otherwise - six cameras on a 390x844 screen would be 120 px tall - it falls back to Fit's layout, six 16:9 full-width tiles with the page scrolling and nothing cropped. The toolbar row stays above the grid in a window (about 40 px, so the tiles cover 95.5 % of the space below the header, measured; in fullscreen the toolbar floats over the grid and the tiles cover 99 % of the screen). The modal always uses `contain`. Toggling only changes CSS custom properties on the grid: no connection is opened, closed or rebuilt (the `livepage` check asserts no `POST` or `DELETE` and an unchanged session count). The choice shows as `fit=fit|fill` in the diagnostics line and as `mode` in `window.__liveStats()` and `window.__liveProbe()`. There is no keyboard shortcut; the buttons are enough.

**Click a tile for one camera, large.** A click (anywhere on the tile except Unmute and the chip) opens a **modal** over a dimmed page: that camera only, as large as the window allows, with its name, state chip, **Unmute/Mute**, **Fullscreen**, **Copy diagnostics** and **Close**. Esc, a click outside the picture, **Close** and the browser's Back button all close it; focus returns to the tile. The grid underneath is not touched - no reflow, no reconnect, the other tiles keep playing. The modal appears at once with the tile's own picture (the same stream, enlarged, no new connection) while it opens ONE new session on the camera's **main** stream; when that has drawn its first frame it replaces the small picture without a flicker (chip **HD loading...**, then **HD**). If the main stream cannot be had, the small picture stays and the chip says **HD unavailable** with **Retry HD**; the modal is never blank. Pressing the mouse or a finger on a tile starts that main session about 100 ms early; releasing elsewhere, scrolling away or no click within half a second drops it again. Sound in the modal is muted until its own Unmute is pressed, the choice survives the swap to the main picture, and a tile's mute is independent. Closing the modal closes its session; only one main session exists at a time. While the page is hidden the modal stays open but its session closes, and it returns when the page is shown again.

**A wall that stays on: hidden means "keep, then free".** Minimizing the window or choosing another camui tab does NOT close the streams at once: they stay connected for a **grace period** and are freed only after it, so a window that is minimized for a minute and brought back shows its pictures again within a second, with no new session. The period is camui's, not the recorder's: `liveHiddenGraceSeconds` in `camui.config.json` (default **300**; `0` frees at once, the old behaviour; `-1` never frees; capped at 86400), or the environment variable `CAMUI_LIVE_HIDDEN_GRACE`, which wins; restart camui to change it. camui hands it to the page as `hiddenGraceSeconds` in `GET /api/live`. After the period every session is closed (`DELETE` sent, the camera's second stream released a few seconds later) and returning to the page reopens the tiles (about 3 s to six moving pictures in the measured rig). The expiry does not trust one long timer: the time hidden is `Date.now()` minus the moment the page was hidden, checked by a 1 s interval and again on every wake-up (return to the page, a thawed page, the network coming back); a hidden page's timers run late, and in a measured Chrome 155 and Edge 155 with a live connection they still fired within about a second of the grace (10 s grace: freed after 10.3 to 11.8 s). A modal that is open keeps its main session through the grace period too. Closing the page or navigating away still closes everything at once (`pagehide`). The pictures themselves are left alone while hidden: pausing the videos, detaching their streams or disabling the video tracks were measured in headed Chrome and Edge and saved nothing beyond what the browser already saves for a hidden page (six tiles: about 21 to 31 % of one core in every variant, the decoder and about 1 MB/s keep running; closing the connections is the only thing that lowers it, to about 5 to 14 %), so no such code runs by default. Keeping the connections costs that CPU for as long as the grace period lasts; the grace is therefore the knob.

**Recovery without a reload.** A tile that had a picture and loses its connection says **Reconnecting** (**Offline** is for a camera that has no picture); it retries after 1, 2, 4, 8, 15, then 30 s with jitter, the delay starts over only once the rebuilt picture really moves, and the whole page makes at most 20 automatic reconnects a minute. When camui reports that live view cannot be reached (503) every tile stops and the next attempt waits 5, 10 ... up to 60 s. The list (`GET /api/live`) is re-read every 10 s, every 5 s while something is wrong and every 30 s while hidden; a failed read keeps what was known, so restarting camui does not touch pictures that are already flowing (media does not pass through camui). **Stall detection:** every 2 s the frames each connected tile has decoded are read; if they do not advance for 8 s the tile is rebuilt ("Picture stalled", not while the page is hidden or just woke up from a freeze). ICE restart is deliberately not used: MediaMTX v1.21.2 has a WHEP `PATCH` for candidates, camui proxies only `POST` and `DELETE`, MediaMTX's own browser reader rebuilds the connection on every error, and a killed server or camera loses the session anyway. Measured on the rig (Chrome 155 and Edge 155, page never reloaded): live MediaMTX killed 14 to 17 s to six moving pictures; camui killed for 6 s no tile noticed and the list was read again about 2 s after camui returned; the camera's stream publisher killed and restarted 8 s later 12 to 19 s; a camera that stops sending 8 to 12 s to detect and about 3 to 7 s to recover; the page's renderer suspended for 40 s (a sleeping PC) about 12 s after the thaw; the live server hung for 70 s about 8 to 12 s after it woke, with 15 session attempts a minute from the page while it was hung. Tiles scrolled out of view (a phone stacks six full-width tiles) stop painting at once if muted and close after 60 s; they reopen when scrolled back.

**Deep links.** `#live` opens the tab (and closes a modal) and `#live/<camera name>` (percent-encoded, case-insensitive) opens the modal for that camera, for example `http://127.0.0.1:8787/#live/Front%20Entrance`. Opening a modal with a click adds `#live/<camera>` to the history so Back closes it; closing it any other way goes back one entry, and a deep link that was typed has nothing to go back to and sets `#live`.

**Needs** (`recorder.config.json`, details in [configuration.md](configuration.md#live-view)): `LiveViewEnabled` `true` (and `RestreamerEnabled`), restart the recorder; optionally `LiveWhepAddress` (default `127.0.0.1:8889`, loopback only) and `LiveSecretPath` (default `%LOCALAPPDATA%\IPCCTV\live_view_secret.txt`). camui reads these keys and the secret file; it never returns any of them.

**How it works.** The browser talks only to camui. camui forwards the WebRTC offer to the live instance with the login added server-side and returns the answer; the picture itself travels from the live instance to the browser directly over UDP on loopback. The browser never sees the instance's address, its login, a path name or a camera address, and no response of the endpoints below carries one: the `uileak` check scans `GET /api/live`, `GET /api/status`, the SDP answer with its headers, every refusal and the static assets for all of them, with a positive control.

| Endpoint | Behaviour |
| --- | --- |
| `GET /api/live` | `{ "enabled", "alive", "cameras": [ { "name", "sub", "main", "camAlive", "restarts", "lastError" } ] }` from `status.json` (redacted). Camera names only; `cameras` is empty when live view is off. |
| `POST /api/live/{camera}/whep?stream=sub\|main` | The body is the browser's SDP offer, `Content-Type: application/sdp`, at most 64 KB. Answers `201`, `Content-Type: application/sdp`, the answer SDP and `Location: /api/live/session/<id>`, an id camui minted. Errors are JSON with generic text: `400` bad `stream` or empty offer, `404` unknown camera or stream not offered or not available, `413` offer too large, `415` not `application/sdp`, `429` too many sessions, `502 live view is misconfigured` (the live instance refused the login, or the secret file is missing or not 64 hex characters, or `LiveWhepAddress` is not loopback), `503 live view is off` or `503 unavailable` (not running, or not reachable), `504` the live instance did not answer in 15 s (a camera source can take up to 10 s to start). An upstream body or header is never returned. |
| `DELETE /api/live/session/{id}` | Closes that session at the live instance and forgets the id: `204`; an id camui did not mint (or one older than an hour) is `404`. A client can only name a session by an id camui minted, never an address. |

- **Caps.** At most **24** live sessions at a time and **6** per camera (a page opens six sub tiles plus at most one modal's main stream, so three viewers fit); more is `429`. A session id is forgotten one hour after it was created: the live instance ends the session itself when the browser's connection closes, and the table only serves the tidy-up `DELETE` and the caps.
- **What goes upstream.** `POST http://<LiveWhepAddress>/<path>/whep` with only `Content-Type: application/sdp` and the Basic login. No browser header (`Cookie`, `Authorization`, `Origin`, `Referer`, `User-Agent`) is forwarded, no proxy from the environment is used, and redirects are not followed. The secret is read from its file at each use and is never logged, returned or stored. A refused login logs **one** redacted line per episode (until the next success), not one per tile.
- **The guard exception.** The request guard requires `application/json` on every state-changing request with a body. A WebRTC offer is `application/sdp`, so exactly one route is exempt: `POST /api/live/{camera}/whep`, with one non-empty `{camera}` segment, and only for that content type. Every other route, method and content type is refused with `415` as before, and the `Host`, `Origin` and `Sec-Fetch-Site` checks apply to the live routes like any other; a page on another origin, a cross-site request or a rebinding `Host` gets `403` and no session reaches the live instance. The `livepage` check proves it with a foreign page in Chrome and Edge and the same requests sent raw, with a positive control.
- **`/api/status` and path names.** `status.json`'s `Live` section carries a `Cameras` list (`Name`, `Sub`, `Main`, and the two path names camui needs). `/api/status` drops `Live.Paths` and those two path names before answering, so no live path name reaches a browser.
- **Checks.** `go test` covers the endpoints against a fake upstream; `uileak` scans the live responses; `livepage` (opt-in, it opens Chrome and Edge windows) plays the six tiles in a real browser at 1920x1080, 2560x1440, 800x1000 and 390x844 and measures the grid (and Fit versus Fill: rectangles, crop, no new session, persistence over a reload, the modal and fullscreen in Fill; `CAMTEST_LIVEPAGE_ONLY=fitfill` runs that part alone), the modal (instant picture, swap to main, grid untouched, close, Esc, backdrop, deep link, Back, pre-warm, failure, hidden window, fullscreen calls), mute and the session counts. `livepage` needs `CAMUI_TEST_EXE` to name a `camui.exe` built from this tree.

**Try it without touching the real system.** `tests\live\demo.ps1` starts a throwaway copy of the rig (the real supervisor with live view on, six synthetic cameras, a camui built to a temp path, non-default ports, fake credentials) and prints the address to open in your own browser.
From a local directory in Windows PowerShell (not from the `\\wsl.localhost` share):
`cd C:\Windows\Temp` then `powershell -NoProfile -ExecutionPolicy Bypass -File <repo>\tests\live\demo.ps1 -Minutes 15`.
Open `http://127.0.0.1:18789/#live`; press Enter in that window, or wait out `-Minutes` (default 15), and it stops exactly what it started and deletes its temp folders.
It builds camui through WSL unless `-CamuiExe` names an exe built from this tree, refuses to start if one of its own ports (18789, 18554, 18557, 18564, 18567, 18889, UDP 18189) is busy, and never uses or touches 8787, 8554, 9997, 8889 or 8189.

## Live view on the LAN: media, firewall and stuck tiles

**A tile that is not playing says why.** Instead of a bare "Connecting", a stuck tile shows, in plain words: the server's answer (`HTTP 201`, or the error), the ICE and connection state, how many candidates the browser and the server offered and of what kind (`1 host (mDNS)`, `1 host (private)`), and `No media after 15 s` when the connection never came up. It also says when the server offers only loopback addresses, which some browsers refuse. Only counts, kinds and an address class (loopback, private, link-local) appear - never an address. **Copy diagnostics** puts one line on the clipboard (browser family and version, stream, the states, the candidate counts, the elapsed time and the verdict) to paste into a bug report; the same line goes to the browser console. The line is `live-diag/3` and also carries milliseconds from the start of the attempt: `gather` (candidates collected), `post` (the signalling round trip), `connected` (ICE and DTLS up), `frame` (the first decoded frame) and, for the modal, `hd` (from the click to the main picture shown), and the policy state: `hidden=<s>` (how long the window has been hidden), `grace=<s>`, `stall=<n>` (stalls found on that tile) and `recoveries=<n>`, and `fit=fit|fill` (the grid mode). Both the tile and the modal have this line, and `window.__liveStats()` returns the same figures. Playing tiles show nothing of this.

**Media on a LAN address.** **Firefox needs this:** it does not connect to a loopback-only media address (Firefox 158 showed `answer=[1 host (loopback)]` and `ice=failed`; with the settings below it plays on the real system, verified by the Operator on 2026-10-16). ## HTTPS on the LAN: a phone or a second PC

An optional second listener serves the whole web app, the Live screen included, over HTTPS to devices on the home network, **behind a sign-in**. It is off by default and the loopback listener (`127.0.0.1:8787`, plain HTTP, no sign-in) is unchanged. There is no plain-HTTP listener on the LAN address and no redirect; a plain request to the HTTPS port gets a bare 400.

**Config** (`camui.config.json` beside `camui.exe`, then restart the UI):

```json
{
  "tlsListen": "192.168.1.50:8443"
}
```

- `tlsListen` is a private IPv4 address of this PC and a port (`10.x`, `172.16-31.x`, `192.168.x`). `0.0.0.0`, names, IPv6, loopback and public addresses are refused. The PC's address should be reserved on the router so it stays put.
- camui **refuses to start** with `tlsListen` set until **at least one user exists** (see below). There is no default account and no default password.
- `tlsReadOnly` (default **true**; env `CAMUI_TLS_READONLY`, flag `-tls-readonly true|false`): the HTTPS listener is **view-only**. A signed-in phone can open the Live and Footage screens and the read-only pages, but `POST /api/control` (start/stop), `PUT /api/config`, `PUT /api/cameras`, record toggles and alert acknowledgements are refused with 403 `read-only: this address can only watch` before any handler runs, and the page hides or disables those controls with a short note. It is an allow-list, so a route added later is refused until it is deliberately allowed; acknowledging an alert is refused too (it is harmless but changes state). Signing in and out is allowed. The loopback listener is not affected. Set `"tlsReadOnly": false` only if you deliberately want a signed-in LAN user to have **full control** of the recorder.
- `tlsHosts` (optional, at most 4): more names the certificate covers, private IPv4 literals or names ending `.lan`, `.local`, `.home.arpa`, `.internal`. The `tlsListen` address, `127.0.0.1` and `localhost` are always included. Anything else is refused.
- `tlsDir` (default `%LOCALAPPDATA%\IPCCTV\tls`) holds the certificate authority and the server certificate with their keys. Keep it private and out of the repository (`*.key`, `*.pem`, `*.crt` and `tls/` are in `.gitignore`).
- `authDir` (flag `-auth-dir`; default `%LOCALAPPDATA%\IPCCTV\camui\auth`) holds `users.json`, `sessions.json` and `auth.log`. It is restricted to your Windows account like the keys. Keep it out of the repository.

### Signing in on the LAN: users, sessions and brute-force protection

**Create the first user** (before, or instead of, starting the LAN listener). Two ways:

1. From a PowerShell window on the PC (the password goes through standard input, so it is never on a command line or in the process list):

   ```powershell
   $c = Get-Credential anna    # a dialog (or a prompt) that does not show the password; the name is only a starting value
   $c.GetNetworkCredential().Password | .\camui.exe -set-password anna
   ```

   Windows PowerShell 5.1 pipes ASCII to a program, so use ASCII characters in the password, or PowerShell 7. Run the same command again to change the password; that also signs the user out everywhere. A user name is 1 to 64 characters from `A-Z a-z 0-9 . _ -` and is not case sensitive. The password is 12 to 128 characters and must not be the user name; there are no other rules (a phrase of a few words is fine).
2. Start camui **without** `tlsListen`, open `http://127.0.0.1:8787/setup` **on this PC** and fill the form. The page exists only on the loopback listener and only while no user exists (afterwards `/setup` and `POST /api/auth/setup` are 404; on the LAN listener they never exist). Anyone who can reach the PC's loopback address can already control everything camui controls, so this page adds no new exposure; it is guarded like every other route (a web page you visit cannot submit it).

Then set `tlsListen`, restart camui and open `https://<this PC's address>:<port>/` from the phone: you get a **login page**. After signing in you see exactly what the token used to give you (view-only by default); the header shows your name and **Sign out**.

**How it works.** The password is stored as `pbkdf2-sha256$600000$<salt>$<hash>` (PBKDF2-HMAC-SHA256, 600,000 iterations, 16-byte random salt, constant-time compare; about 0.3 s per check on the development PC, 270 to 360 ms measured). The scheme and cost are in the string, so a stronger one can be introduced later and old hashes are upgraded the next time their owner signs in. A session is a random 32-byte token in the cookie `camui_session` (`Secure; HttpOnly; SameSite=Strict; Path=/`, persistent for 30 days so it survives a browser restart); the server keeps only its SHA-256 in `sessions.json` (so sessions survive a camui restart). A session ends after **7 days without use** or **30 days after sign-in**, whichever comes first, at Sign out, and when the user's password is changed with `-set-password`. Every sign-in issues a new token. Files are written through a temp file restricted to your account and renamed, and are re-read when `-set-password` changes them while camui runs. The user list is behind a small interface, so a database can replace the file later. `role` is stored (`admin`) but nothing but `tlsReadOnly` is enforced by it yet.

**What needs no session on the LAN listener:** the login page (`/login`, `/login.js`, `/style.css`), `POST /api/auth/login` and `GET /api/auth/me` (which answers `authenticated: false` when you are not signed in). Everything else, static files, `/api/*`, the Live proxy and the CA download included, needs a valid session: a browser navigation is redirected (303) to `/login?next=<path>` and an API call gets 401 `{"error":"authentication required"}`. The `next` target is accepted only as a same-origin path (`//host`, `/\host`, `https://...` and `javascript:` become `/`). A foreign-origin or cross-site POST to the login endpoint is refused with 403 before a password is looked at.

**Brute-force protection.**
- Per client address (the TCP peer; `X-Forwarded-For` is never trusted): 10 sign-in attempts a minute with a burst of 5, then 429 with `Retry-After`. At most 4096 addresses are tracked; idle ones are dropped.
- Per user name, **including names that do not exist** (so the answer never says which names exist): the first 4 failures cost nothing; from the 5th the name is refused for 30 s, doubling with each further failure up to 15 minutes. It is never permanent, a success resets it, and the counter is forgotten after 24 hours of quiet. While a name is locked even the **correct** password is refused (429, `Retry-After`), which is standard. The consequence: someone on your network can keep a given name locked for up to 15 minutes at a time by guessing at it. A device that is already signed in is not affected, because its session does not depend on the lock. To clear it at once run `.\camui.exe -unlock anna` (the running camui applies it at the next attempt for that name); the counters are in memory, so **restarting camui clears them too**. The lock is keyed by user name only, not by (name, address): keying by address as well would let anyone with several addresses guess in parallel, and it does not stop an attacker from locking you out from one address while you are on another; this is revisited when camui is reachable beyond the LAN.
- An unknown user and a wrong password answer identically (`Invalid username or password`, same status, headers and, as far as measurable, time: an unknown name still costs one password hash). A successful sign-in does not mention earlier failures. Request bodies are limited to 4 KB, JSON only.
- `auth.log` in the auth folder records time, peer address, the attempted user name (cut to 64 characters, control characters removed) and the result (`ok`, `fail`, `throttled`, `locked`), plus sign-outs and `-set-password` / `-unlock`. Never a password, a hash or a token. It is append-only, capped at 1 MiB, and then becomes `auth.log.1` (one older file is kept).
- The console log carries the same facts as structured records (`component=auth action=auth.login actor=... target=<user name> result=ok|fail|throttled|locked duration=...`; actions `auth.login`, `auth.logout`, `auth.lockout`, `user.set_password`, `user.unlock`, `user.create`): INFO for what succeeded, WARN for a failed, throttled or locked sign-in, ERROR for a store failure, DEBUG for the address limiter's decisions. Never a password, a hash or a token at any level.

**Windows Firewall** (not applied for you; run in an elevated PowerShell, adjust the port): allow the page and the media from this subnet on Private networks only.

```powershell
New-NetFirewallRule -DisplayName 'IPCCTV camui HTTPS (TCP 8443)' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8443 -Program '<path to camui.exe>' -Profile Private -RemoteAddress LocalSubnet
Remove-NetFirewallRule -DisplayName 'IPCCTV camui HTTPS (TCP 8443)'   # to take it away again
```

The video itself needs the media settings and the UDP rule from [Live view on the LAN](#live-view-on-the-lan-media-firewall-and-stuck-tiles).

**The certificate authority.** The first start (or `camui.exe -print-ca`) creates a local CA, ECDSA P-256, valid 10 years, and the server certificate it signs. The CA is limited by X.509 name constraints to private addresses (10/8, 172.16/12, 192.168/16, 127/8) and the names `localhost`, `.lan`, `.local`, `.home.arpa`, `.internal`: a leaked CA key cannot vouch for a public website (a test proves the standard verifier refuses `example.com` and a public IP). The server certificate lasts 390 days and is replaced automatically when it is near expiry or when the addresses it must cover change (a new LAN address is just a restart); devices keep trusting the CA. Keys are written through a temp file restricted to your Windows account (`icacls`, inherited access removed) before any secret goes into it, then renamed; only the CA **certificate** is ever served (`/api/tls/ca.crt`, to a signed-in user; it is a 404 on the loopback listener). `camui.exe -print-ca` prints its path and SHA-256 fingerprint.

**Install the CA once per device, in this order.** The download needs a session, so: (1) open `https://192.168.1.50:8443/` on the new phone and click through the one certificate warning, (2) sign in, (3) **Settings > Connect a phone** and download the certificate (or copy the file by other means), (4) check the fingerprint the device shows against `-print-ca` before trusting it, (5) install it, (6) reopen the page: no warning any more.
- **iPhone/iPad:** open the file, then Settings > General > VPN & Device Management > the profile > Install; then Settings > General > About > Certificate Trust Settings > switch the root on. On some iOS 18 builds the root may not appear in that list (unverified here).
- **Android:** save the file, Settings > Security > Install a certificate > CA certificate. Chrome trusts a user-installed CA; some apps do not.
- **Windows:** double-click the file > Install Certificate > Trusted Root Certification Authorities. **macOS:** Keychain Access > import > set to Always Trust. **Linux:** your distribution's `update-ca-certificates` procedure, or the browser's own certificate manager.

**Rotate or revoke.** Delete the `tlsDir` folder and restart camui: a new CA and certificate are created; remove the old CA from each device and install the new one. To cut one person off, change their password with `-set-password` (it ends their sessions); there is no per-device list yet.

**Threat note.** The sign-in and the HTTPS keep other devices out and the traffic private on the LAN. With `tlsReadOnly` on (the default) a lost phone or a guessed password can watch but cannot stop recording or reconfigure anything; with it off a signed-in user is full control. Anyone who can read `tlsDir` can read the private keys: with the CA key they can mint certificates for private addresses and `.lan`-style names (not public ones), and with the server key they can impersonate this PC to a device that trusts the CA. Anyone who can read `authDir` can read the password hashes (slow to attack, but not nothing) and the hashes of the session tokens (not usable as tokens). Keep both folders private (they are restricted to your account) and do not copy them. This does not make camui safe to expose to the internet: that needs more than a login (see the plan, Stage 3).
