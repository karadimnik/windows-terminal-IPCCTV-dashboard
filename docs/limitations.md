# Known limitations

These are measured, not theoretical. None of them is hidden in the code.

1. **Cameras serve exactly two concurrent RTSP sessions.** Measured on all six here and consistent with TP-Link's documentation, so it is firmware policy rather than a bug. The dashboard plus the recorder uses both slots, leaving nothing for the phone app, a browser preview or an ad-hoc `ffprobe`. The relay exists to turn those two slots into one.
2. **If the dashboard and the recorder are both already on direct inputs, MediaMTX can never pull.** Both slots are taken and there is no third for the relay. Restart either consumer and it will pick the relay up.
3. **MediaMTX path names must be lowercase alphanumeric.** Its environment variable key is cut at the first underscore, so a path named `workshop_entrance` silently creates a stray `workshop` path and leaves the real one unserved, with nothing logged. The generator lowercases names and strips non-alphanumerics for exactly this reason. Do not hand-edit the generated config.
4. **The camera password reaches ffmpeg, mpv and MediaMTX in the clear.** That is the floor: none of them has an out-of-band credential source, so the URL has to arrive somehow. MediaMTX gets it on its environment block, which is not visible to the process listings any user can read. Another process of the same Windows account can still read that environment, and the process's memory. A consumer on a **direct** camera input gets it inside the RTSP URL on its own command line, which is: that covers `ffmpeg` whenever the relay is not serving that camera, and the `ffprobe` and `ffmpeg` calls `-SelfTest` makes, which always address the cameras directly. `mpv` is no longer on that list: a viewer pane hands it the URL over a private control pipe. **Closed:** the relay's control API used to answer any local process or Windows account without a login, and its `/v3/config/paths` routes returned a camera's full source URL. It now requires the product's own login: a random secret generated by `-InstallRestreamer` (or by the first supervisor start that finds none) and kept DPAPI-protected in `relay_api_creds.xml` beside the scripts, with only its SHA-256 in `mediamtx.yml`. Without it every route answers 401 and carries no password, and the API still sends no cross-origin permission. A login the relay refuses is treated as a configuration fault, never as a dead relay: every consumer stays on the relay and alert 130 is raised once, so the fault cannot push the password back onto a command line. Running the relay is what keeps everything else off that path. Nothing is written to disk, and every log line and console message is redacted to `rtsp://***:***@host/stream1`.
5. **Segment boundaries overshoot the clock mark by up to one GOP**, because a stream copy can only cut on a keyframe.
6. **Tapo cameras keep a separate account for RTSP**, distinct from the TP-Link cloud login. Changing the cloud password does not affect RTSP. To change the RTSP credential, delete `camera_creds.xml` and run the dashboard again.
7. **Some paths have fired only in a sandbox, never on the live NVR:** log rotation at `LogMaxBytes`, the backoff reset at `HealthyResetSeconds`, the stall watchdog, the age cap `MaxRetentionDays` with the pruner's deletions, and the pruning alerts 121 and 122. Each has run inside a real supervisor recording a synthetic camera at scaled-down thresholds (harness checks `logrotatelive`, `backoff`, `stallwatch` and `pruneloop`). The production segment length is no longer on that list: real 15-minute segments have been measured under `ffprobe` and hold the 900 s mark to within a tenth of a second.
8. **Several tuning keys are absent from `recorder.config.example.json`.** They are marked * in [docs/configuration.md](configuration.md); add them by hand if you want to change one.
9. **The test harness leaves its sandbox behind on purpose**, under `%TEMP%\cam-tests\<check>`, so you can inspect what a check did. The credential copy it makes is always deleted; footage a live check recorded is not. Delete the folder when you are done with it.
10. **Autostart depends on the recorder's path being reachable at logon.** If the repository lives inside WSL, the launcher polls `\\wsl.localhost` for up to 300 s and the task then retries up to three times, but nothing records while WSL is down. Keeping the repository on a local drive avoids the wait entirely. The launcher log at `%LOCALAPPDATA%\IPCCTV\autostart.log` is the first thing to read if autostart did not work.
11. **The footage player cannot seek ahead of what has arrived.** A clip is remuxed on demand and streamed, so the response carries `Accept-Ranges: none` and no length, and the browser can only seek inside what it has already buffered. Nothing is lost, it is just a wait: once the whole clip has arrived it is all seekable.
12. **Two harness checks always skip on a live NVR.** `autostart` refuses to run while a task named `IPCCTV-Recorder` is registered, because it would rewrite and then delete the real autostart, and `procs` refuses while the recorder is running, because the processes it hunts for already have a legitimate owner. On this machine both skip permanently. How many skip is not a constant: `leak` and `uileak` skip as well on a machine with no `camera_creds.xml`, and `uileak` and `uiguard` skip if `camui.exe` is not there to start - so read the tally the harness prints.
13. **`status.json` reports configured relay paths, not ready ones.** The strip says `N path(s)` and tells relay from direct per camera in its `MODE` column, which is the honest signal; do not read the count as readiness.
14. **A daylight-saving change moves nothing; a step of the clock itself still does.** Every interval is measured in UTC, which a daylight-saving change never touches. That has been shown in a sandbox - harness checks `dst` and `dstloop` simulate both transitions of this zone without moving the machine clock - but not yet at a real transition on the live NVR; the next is 2026-10-25 at 04:00. A step of the UTC clock itself, such as a manual change or a large time-sync correction, is a different event. Measured in a sandbox: a step forward of an hour costs one watchdog restart and one alert 110 per camera, then everything carries on; a step back of an hour freezes the status, reconcile, archive-scan and prune timers until the clock catches up, so `status.json` goes stale and the health strip and `-Status` report the supervisor as not running while ffmpeg keeps recording. Read from the code, not measured: during that hour the watchdog is blind and a restart that was already scheduled waits for the hour too. The few-second corrections of a normal time sync are far inside every threshold.
15. **Under Holocron a camera folder holds day folders, and the PowerShell system cannot read them.** Holocron files closed segments into `<Camera>\YYYY-MM-DD\` (decision D20, which replaced D18's unchanged layout); File Explorer shows each day as an ordinary folder inside the camera folder, with only the open segment and the newest closed one beside them. The PowerShell recorder and pruner list only the files directly in a camera folder (`Get-ChildItem -File`), and so does the Footage screen of the old `camui.exe` (read from its source; the installed executable was not run), so over a filed archive they would show and prune nothing that is filed. Going back therefore needs `holocron down`, then `holocron archive flatten --now` ([rollback R2a](rollback.md#r2a-put-the-archive-back-flat)). Segments cannot be filed while another process holds them open (Windows): the next mover cycle retries.
