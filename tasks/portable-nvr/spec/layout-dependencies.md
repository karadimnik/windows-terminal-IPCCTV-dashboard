Repository: <repo>, branch portable-nvr. Read-only research.
All paths below are relative to that repository unless absolute. "Go" = module `holocron`; "PS" = legacy PowerShell system.
"Nested" means `<camera>/<YYYY>/<MM>/<DD>/<file>` or `<YYYY-MM-DD>/<camera>/<file>`; where the two behave differently both are given.

## 0. The layout as it is (verified)

- Pattern: `<RootPath>/<safe>/<safe>_%Y%m%d_%H%M%S%z<ext>` built in ONE Go place, `internal/ffmpeg/args.go:132-135` (`SegmentPattern`), which doubles every `%` of root, folder and file name (`args.go:133`). The leaf comes from `internal/archive/segment.go:30-32` (`FormatSegmentPattern`). PS twin: `cam.common.ps1:1964-1981` (`Get-CamSegmentPattern`), `cam.common.ps1:1925-1961` (`Get-CamPaths`), `cam.recorder.ps1:3608-3628` (`New-CamChildFor`).
- `<safe>` = `archive.SafeName` (`internal/archive/names.go:44-72`), a port of `Get-CamSafeName` (`cam.common.ps1:720`). The camera folder name, the file prefix and the `IsSegmentOf` test are all this one string (`internal/archive/scan.go:83`, `internal/archive/segment.go:187-194`).
- Root children starting with `_` are system folders: `_state` (`internal/app/paths.go:26-34`, `internal/osx/env.go:78`), `_logs` (`paths.go:27`, `internal/supervise/loop.go:343`), `_state/inputs` (`loop.go:330`). `_config` and `_mtx` appear only in tests and `docs/shadow.md:75`, `docs/cutover.md:52,135` (shadow/rehearsal roots), not in any non-test Go code (grep `_mtx|_config` over *.go: only `internal/supervise/relayext_test.go:122`, `sup_helpers_test.go:426-427`, `internal/app/shadow_unix_test.go:26`).
- The ownership marker: `<root>/_state/archive-owner.json` (`internal/archive/marker.go:37`), same content as PS (`cam.common.ps1:2928-2990`).
- No configuration key names a path template. Keys involved: `RootPath` (`internal/config/parse.go:260`, must be non-blank and contain no `%`, `parse.go:518-523`), `SegmentSeconds` (`parse.go:263`, default 900 `config.go:114`), `Container` + `ContainerProfiles` (`parse.go:264,367-428`; the `Extension` decides what the pruner may delete, `parse.go:412-416`; defaults `config.go:117-123`), `StatusIntervalSeconds` 5, `ArchiveScanSeconds` 60, `PruneIntervalSeconds` 300, `ReserveGB` 20, `MaxRetentionDays` nil (`config.go:~125-141`, see Defaults()). ## NEW FACT from the Operator: the segment muxer does not create folders

- Corroborated in the repo: `cam.common.ps1:1927-1929` ("The segment muxer cannot create directories (-strftime_mkdir is on the hls muxer only), so every directory must exist before ffmpeg starts"); `cam.recorder.ps1:3611-3613`; history: `tasks/ipcctv-recording/todo.md:1247` item [83] (a date-partitioned layout `<Cam>\<YYYY-MM-DD>\...` was proposed and DROPPED by the Operator on 2026-10-14 for exactly this reason: "Failed to open segment", exit -2, `-strftime_mkdir` has no effect, "the supervisor would have to pre-create tomorrow's folder or recording dies at midnight - plus changes to seven readers"); `tasks/portable-nvr/spec/inventory-recorder.md:113`; decision D18 "Archive layout and file names: Unchanged, so both systems can share footage" (`tasks/portable-nvr/os-independent-hld.md:231`). `-strftime_mkdir` is not used anywhere in Go or PS code (grep: only the comments above).
- Go today creates the folder in exactly one place and only at child spawn: `internal/supervise/loop.go:308` (`os.MkdirAll(e.Dir(), 0o755)` inside `cameraSpec`, called from `startCamera` `loop.go:~246-262`). Nothing creates a folder while a child is running. The inventory itself records "what happens if a camera folder is deleted while running: the supervisor does not re-create it ... [UNVERIFIED]" (`inventory-recorder.md:113`). A long-running child crosses midnight (or a month/year folder boundary) with no hook.
- Component that would own pre-creation: `internal/supervise` (the Supervisor loop). It already owns the spawn-time mkdir (`loop.go:308`), the per-camera `Entry.dir` (`manager.go:208,356`), and a 1-second tick (`loop.go:41,57-58`; `Deps.Tick: time.Second` `supervisor.go:360`) with a 5-second status sub-tick (`loop.go:73-83`). `internal/ffmpeg` only builds the pattern string (`args.go:132`) and has no clock or filesystem duty besides `RemoveEmptySegment`/`WriteInputList`; `internal/archive` owns the name rules (the date-folder name would belong there). The bounded hook points are `loop.go:61-90` (`tick`) and `cameraSpec` `loop.go:305-346`.
- Where "next boundary" is already computed in code: NOWHERE in production Go or PS. Segment cutting is done by ffmpeg itself (`-segment_atclocktime 1`, `args.go:114`; PS `cam.common.ps1:2025`); SP1 recorded that it cuts on multiples of N seconds counted from LOCAL midnight (`tasks/portable-nvr/os-independent-lld.md:302`). The only Go arithmetic on that rule is the post-hoc check `aligned()` at `internal/shadow/compare.go:734-743` ((unix + zone offset) mod segSeconds within a tolerance) used by `boundaries()` `compare.go:748-759`; the only forward computation is in the PS test harness `tests/cam.tests.ps1:5026-5030` (soak test picks the next quarter hour). Also relevant: boundaries "overshoot the mark by up to one GOP" (`docs/how-it-works.md:19`) and the first segment after any (re)start begins at an arbitrary second (`how-it-works.md` sample `223649`), so a new date folder is needed at the START of whichever segment opens first after the boundary, and also at any restart (the spawn-time `MkdirAll` at `loop.go:308` would need to create the folder for "now" and for the next boundary). Which clock ffmpeg's strftime uses for the directory part (segment open time vs the time the muxer evaluated the pattern) is UNVERIFIED here; `args.go:129-131` states `-strftime 1` expands the WHOLE path (measured with 4.2.7), so directory components are subject to `%` doubling already handled at `args.go:133`.
- Failure mode if the folder is missing when the next segment opens: the muxer fails, ffmpeg exits (per [83]: exit -2), `Manager.Exited` applies backoff (`internal/supervise/manager.go`, BackoffStartSeconds 3, Max 60) and respawn goes through `cameraSpec` (which would create "today"), so the loss is bounded by the restart but is a restart with a segment gap, and alert 110 can trigger only after max(15 min, 935 s) (`internal/supervise/down.go:21-25`).

## 4. Status rows and the supervisor (`internal/status`, `internal/supervise`)

Scan frequency (defaults `internal/config/config.go`: StatusIntervalSeconds 5, ArchiveScanSeconds 60, PruneIntervalSeconds 300):

- Per status tick (every 5 s, `loop.go:73-83`): `Manager.Refresh()` (`internal/supervise/stall.go:15-31`) calls `Scanner.Scan(e.dir, now)` for EVERY entry (`m.sorted()`): `ArchiveScanner.Scan` (`stall.go:106-116`) -> `Matcher.Scan`: 1 `os.ReadDir` of the camera folder (sorted by name), `DirEntry.Info()` for every file, 1 `LiveSize` open of the newest. 12 per minute per recording camera. Then `Manager.Down()` (`loop.go:78`) reuses the scans.
- Once per `ArchiveScanSeconds` (60 s, inside the status branch, `loop.go:79-82`): `scanArchive` -> `ArchiveScanner.ScanRoot` (`deps.go:73-118`): `ReadDir(root)`, `Lstat` of every non-`_` entry (`:88`), then a full `Scan` of each camera dir (a second full listing, second `LiveSize`). 1 root listing + 1 listing per camera per minute.
- Once per `PruneIntervalSeconds` (300 s, `stop.go:17-29`): `prune.Collect` -> 1 `ReadDir(root)`, per camera 1 `ReadDir` + 1 `os.Lstat` PER FILE (`collect.go:53`) + 1 `Matcher.Scan` (another `ReadDir`+Info per file, `collect.go:62`); `CheckRoot`, `VerifyRoot` (Lstat + read of the marker) first. 0.2 runs per minute.
- On every ffmpeg exit/kill: `RemoveEmptySegment` = 1 `ReadDir` + `Lstat` per file (`empty.go:44-53`).
- Totals per recording camera per minute at defaults: 12 + 1 + 0.4 = 13.4 `ReadDir` calls of the camera folder (plus 1.2 root listings per minute for the whole archive). Entries touched per camera per minute = 13.4 x N (N = files in the folder): with 96 segments/day x 2.5 days = 240 files that is about 3,200 entries/min/camera (about 19,000 for the six cameras documented in `docs/how-it-works.md` "All six of these cameras"; the camera count of the live system is not verifiable from the repo); with 10x the files it is about 32,000/min/camera. Plus 0.2 x N explicit `Lstat` per minute per camera from the pruner. On Windows `DirEntry.Info()` is served from the directory listing (standard-library behaviour, not verified in this repo); on Linux each `Info()` is an `lstat` (same caveat). The live-size open (`archive/livesize_windows.go`) is 13 per minute per camera regardless of N. Sorting: `ReadDir` sorts by name, O(N log N) per call. Cost scales linearly with N per call and there is no caching of previous listings.
- Why this matters for a redesign: with a nested layout the per-tick scan only needs the newest day folder (plus the previous at midnight), so per-tick cost becomes proportional to one day (96 files) instead of the retention window; the whole-archive scan (`ScanRoot`, prune `Collect`) still needs a recursive listing.

What happens if Holocron writes a nested layout and the PS system is started again over the same root (consequences read from the code above; not run):
1. PS `Get-CamPaths`/`New-CamChildFor` creates (or finds) `Root/<safe>` and ffmpeg writes NEW flat segments into the camera folder: a MIXED tree (old nested days + new flat files).
2. PS pruner (`-File`, immediate children only) never sees nested files, so they are never pruned, and the disk fills until the reserve is breached; the pruner then reports blocked/nothing deletable (alert 121 in PS terms: pruning continues for the flat files only). No directory is ever removed.
3. PS `Get-CamDirScan`/status/down-alert logic only sees flat files: after the swap back there are none until the first PS segment closes, so `SecondsSinceLastClosedSegment` and the stall/down alert behave as at any fresh start (the D19 floor, `down.go:30-34`); not a new fault.
4. The PS claim rule would refuse to RE-claim (a "folder inside a camera folder" blocker, `cam.common.ps1:2974-2977`) if the marker were ever invalid; with the marker intact PS prunes flat files only.
5. The old `camui.exe` footage screen (flat, one `ReadDir` per camera) shows only the flat files: the nested days vanish from the UI; the footage is still on disk.
6. Docs promise the opposite today: `docs/rollback.md:132` ("Holocron's segments are in the same folders with the same names and format as the old system's ... the old pruner recognises them by name and container alone ... so they age out like any other file. The Footage screen of the old UI lists them by file name"), `docs/cutover.md:27`, decision D18. A nested layout breaks D18 and that rollback paragraph.
Net: with nested folders the rollback path loses pruning and Footage visibility of everything written by Holocron, and the only safe way back is a flat layout or a conversion step run before PS is restarted.
