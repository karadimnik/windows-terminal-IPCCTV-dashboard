# holocron

The one executable (rule R1). Every command is a `cli.Action` registered once (`commands.go`) and run by `cli.Runner`, so
its begin (DEBUG) and result (INFO mutating ok, DEBUG read-only ok, WARN refused, ERROR failed) are logged with action,
actor `cli:<os user>`, target, action_id, pid, duration (rule R2). `TestEveryCommandIsAnAction` asserts the exposed list.

    holocron [--root DIR] [--config FILE] [-v|-vv] [--json] <command> [arguments]

`--root` overrides `RootPath`; `--config` defaults to `holocron.config.json` in the platform's configuration folder and
`cameras.json` sits next to it. `-v`/`-vv` set DEBUG/TRACE for that invocation and mirror the records to stderr. Records go
to `<root>/_logs/holocron.log`, mutating ones also to `audit.log` (install, uninstall and autostart all; their steps on
component `install`: the exact commands and generated files at DEBUG, state changes at INFO, failures at ERROR). With `HOLOCRON_SANDBOX_ONLY=1` a root that is a drive or
filesystem root, has a folder named `cameras` in its path, or holds PowerShell recorder files is refused (exit 2).

**The web child (`up`).** `app.RunHost` hands the host an `Aux` (internal/host): `<exe> <global flags> web --stop-file <state>/web.stop` in the host's own scope, restarted in place after 5 s (then 10, 20, 40, 60 s; 300 s of health resets), a WARN each time, alert 104 (Error) at 5 crashes in 30 minutes; a web crash never stops or restarts the supervisor and a supervisor restart never restarts the web. It is listed in `_state/aux.json` (role `web`), a file of its own because the supervisor's start-up reap empties `children.json`. Before it starts, a web child left by a crashed host is reaped when provable and no other host is alive. `up` prints `web app: http://<listen>/ is answering` after the `RECORDING` line (it waits up to 10 s and never fails `up` over it).

Exit codes: 0 ok, 1 failure, 2 usage (also a sandbox refusal), 20 another supervisor holds the archive, 21 configuration
fault (a missing camera login names `HOLOCRON_CAMERA_USER` / `HOLOCRON_CAMERA_PASSWORD`; ffmpeg below 5.0).

The camera login comes from the two environment variables `HOLOCRON_CAMERA_USER` and `HOLOCRON_CAMERA_PASSWORD` when
both are set (they win), otherwise from the secrets store the configuration selects (`camera.user` and `camera.password`,
see `secret set` and `secret import`); a login missing from both is a configuration fault (exit 21) that names the two
variables and the `holocron secret set` commands. No credential is ever on a command line or in a file this command
writes. The control API is described in `internal/ctlapi/README.md`.

## Tests

`go test ./cmd/holocron` runs the unit tests with a fake control client and status files in `t.TempDir()`.
The end-to-end run is opt-in and was run on Windows (WSL builds both binaries; MediaMTX is a copy in the test's temp folder,
ports 18740-18742 only, every other listener off; the relay's listener set is checked with `netstat -ano`):

    GOOS=windows go build -o /mnt/c/Windows/Temp/holocron-w9a/holocron.exe ./cmd/holocron
    GOOS=windows go test -c -o /mnt/c/Windows/Temp/holocron-w9a/holocron.test.exe ./cmd/holocron
    cd /mnt/c/Windows/Temp/holocron-w9a && HOLOCRON_IT=1 HOLOCRON_IT_FFMPEG='C:\ffmpeg\bin\ffmpeg.exe' \
      HOLOCRON_IT_MEDIAMTX='C:\mediamtx\mediamtx.exe' HOLOCRON_IT_EXE='C:\Windows\Temp\holocron-w9a\holocron.exe' \
      TMP='C:\Windows\Temp\holocron-w9a\scratch' TEMP='C:\Windows\Temp\holocron-w9a\scratch' \
      WSLENV=HOLOCRON_IT:HOLOCRON_IT_FFMPEG:HOLOCRON_IT_MEDIAMTX:HOLOCRON_IT_EXE:TMP:TEMP ./holocron.test.exe -test.v -test.run TestEndToEnd

Scenario: `up --detach` -> both lavfi cameras alive and writing segments -> `cam disable cam2` stops it, cam1 goes on ->
`log level supervisor debug` makes DEBUG supervisor records appear -> `config set MaxRetentionDays 30` -> `down` with
0 survivors (the web child included), final `stopped/requested`, `ctl.addr`, `ctl.secret`, `host.json` gone, the fake password in no file -> a
second `down` reports nothing running. Since W9b the same run also covers the web app on the first free port of 18820-18839
(`web.listen`, `web.authDir` and `web.tlsDir` in the scratch folder): `GET /api/status` is valid JSON with `controller: api`
whose camera rows equal `holocron status --json`; `POST /api/cameras/cam2/record` `{"enabled":false}` stops that camera through
the control API (cameras.json shows it off, the supervisor's records carry `actor=web:loopback`) and `true` starts it again;
the web child killed by pid is answering again after about 5 s with the supervisor pid unchanged and cam1 still writing
segments. Measured 2026-10-20 (Windows 11, from WSL): web answering with `up` (2.2 s to the honest start), toggle off took
effect 1.8 s after the request (the response itself 20 ms), web restart after the kill 5.5 s, `down` 0.4 s with 0 survivors,
whole test 37.9 s. Measured 2026-10-20 (Windows 11, from WSL): first valid status 1.7 s after `up`,
stop 0.4 s, 0 survivors, whole test 31.8 s. Launched from WSL interop the terminal's job refuses breakaway; `up` then says
so (the background copy stays in that job).
